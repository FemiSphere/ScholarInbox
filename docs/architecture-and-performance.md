# 项目结构与性能分析

本文记录 ScholarPulse 当前的数据流、模块职责、LLM 调用方式和已观察到的性能瓶颈。分析基于 2026-08-20 的代码与本地 `logs/`；本文只提出优化方向，不改变现有执行逻辑。

## 1. 执行链路

入口是 `literature_digest.cli:main`：

1. 读取 `.env`、主 YAML 和独立 LLM YAML。
2. 从 Gmail 搜索消息列表，再逐封下载完整 MIME 内容和所需附件。
3. 按发件人、主题和营销关键词过滤邮件。
4. 解析论文条目：
   - Google Scholar 邮件使用本地 HTML/文本规则。
   - 其他期刊、出版社和 RSS 邮件默认逐封调用 LLM 做结构化抽取；失败时回退到本地解析器。
5. 按 DOI、URL、规范化标题和模糊标题相似度去重。
6. 读取最近 Markdown digest，再次过滤近期已输出论文。
7. 调用一次 LLM 提炼 `research_interests.md`。
8. 以每批 20 篇论文调用 LLM，完成相关性、中文标题、摘要和推荐理由。
9. 本地生成 Markdown 与 HTML。
10. 非 dry-run 且配置允许时，逐封把已处理邮件标记为已读。

## 2. 关键模块

| 模块 | 职责 |
| --- | --- |
| `cli.py` | 编排完整工作流、进度和运行模式 |
| `gmail_client.py` | OAuth、Gmail API、MIME/附件读取、代理与超时 |
| `email_filter.py` | 邮件级过滤 |
| `parsers.py` | 本地解析与非 Scholar 邮件的 LLM 结构化抽取 |
| `dedupe.py` | DOI、URL、标题和模糊标题去重 |
| `recent_outputs.py` | 从近期 Markdown 输出恢复论文身份用于跨次去重 |
| `interests.py` | 研究兴趣读取、LLM 提炼和本地回退 |
| `ranking.py` | 每批 20 篇的 LLM 排序、翻译和摘要 |
| `digest.py` | Markdown/HTML 渲染和输出命名 |
| `llm/` | Codex CLI、OpenAI-compatible API 和离线样例客户端 |

## 4. 当前主要瓶颈

### 4.1 排序批次完全串行

`ranking.rank_papers()` 把论文按 20 篇分批，然后在普通 `for` 循环中依次调用 `llm.complete_json()`。例如 2026-08-19 提取的 426 个条目在两轮去重后剩余 276 篇，需要 14 个排序请求，再加一次兴趣提炼；任一请求的网络等待和模型生成时间都会直接累加。

这是当前最稳定、最主要的延迟来源。

### 4.2 非 Scholar 邮件逐封串行结构化

`parsers.parse_emails()` 对每封非 Google Scholar 邮件调用一次 LLM，仍使用串行循环。出版社邮件较多或单封正文较长时，解析阶段会从几秒增长到几十秒甚至更久。

每个请求最多携带约 9000 字符邮件正文、80 个链接和 40 个图片候选。长 prompt 会增加输入 token、传输量和首 token 延迟。

### 4.3 每次运行都重新提炼研究兴趣

配置中已有 `research_interests.refresh_each_run`，但当前主流程没有利用它做缓存判断：只要存在候选论文，就会重新调用一次 LLM 提炼同一份 `research_interests.md`。这不是最大瓶颈，但属于稳定的固定成本。

### 4.4 JSON 失败会把单次请求成本翻倍

OpenAI-compatible 与 Codex CLI 客户端在 JSON 解析失败时会完整重试一次。这个回退对可靠性有必要，但如果批次过大、输出 token 不足或服务偶发返回空内容，单批延迟会接近翻倍。当前日志没有记录每次重试和 token 用量，因此暂时无法量化发生率。

### 4.5 Gmail 与已读标记逐封请求

邮件列表只需一次请求，但完整邮件、附件和已读标记逐封执行。8 月 19 日读取 64 封邮件约用 37 秒，最终写出和标记已读约用 32 秒。它们是次要瓶颈，但在 LLM 加速后会变得更显著。

### 4.6 缺少可观测性

当前日志能看到大阶段耗时，却没有以下信息：

- 每个 LLM 请求的用途、批次大小和耗时；
- 首次响应还是 JSON 重试；
- 输入/输出 token 和缓存命中；
- 非 Scholar 邮件结构化调用数；
- Gmail 单封读取、附件下载和已读标记耗时。

因此目前能确定“慢在哪里”，但还不能精确判断最合适的并发数、批大小或 token 上限。

## 5. 后续优化优先级（尚未实施）

1. **先补计时与 usage 日志。** 为每类 LLM 请求记录用途、批次、耗时、重试和 API `usage`，不记录 prompt 正文或密钥。
2. **为排序批次增加有限并发。** 建议先从 2–4 个 worker 试验，并保留原始 index 后稳定合并结果；同时处理 HTTP 429、超时和指数退避。
3. **为非 Scholar 邮件结构化增加有限并发。** 邮件之间天然独立，但需要限制总并发，避免与排序请求互相抢占。
4. **按研究兴趣文件哈希缓存兴趣画像。** 只有 `research_interests.md` 内容或模型配置变化时才重新提炼。
5. **减少 prompt 体积。** 先用本地规则压缩导航、页脚、重复链接和无关正文，再发给 LLM；对低信息邮件直接使用本地解析。
6. **评估批大小。** 20 篇不是经过基准测试的最优值。批次太小会增加往返次数，太大会增加首 token 延迟、JSON 截断与整批重试成本。
7. **最后优化 Gmail I/O。** 可评估 Gmail batch 请求、并发下载或批量已读标记，但必须保持“不删除邮件”和 dry-run 边界。

DeepSeek 当前官方文档允许较高并发，但实际可用并发仍受账号、服务状态、请求大小和本地网络影响。项目不应直接按平台上限启动大量请求；应先通过日志和小规模基准确定安全值。官方参考：[模型与价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[限速与隔离](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit)、[JSON Output](https://api-docs.deepseek.com/zh-cn/guides/json_mode)。
