# 长邮件分块提取与截断恢复（2026-10-20）

## 问题与调整

最新运行的两次回退来自 PRL 周报和 JACS 新文章通知：提取输出与 JSON 修复输出都达到 4000 token，并以 length 结束。后续排序和翻译成功，所以 HTML 可读，但源邮件提取不保证完整。

当前本地配置仅把 email_extraction 输出上限提高到 8000 token；排序仍使用 high 思考模式，提取与翻译仍为非思考模式，模型名和 API key 未更换。修改前私有配置备份位于 `data/config_backups/20261020-004403-long-email/`，不进入 Git。

## 处理流程

1. HTML 按有序正文、论文标题链接、图片引用与结构边界分组；以每块最多约 8 个识别出的论文候选、12000 字符、50 个候选链接、20 个图片引用控制大小。排版表格行不直接计作论文。无法可靠识别条目的复杂格式则按有序正文窗口划分，保留边界重叠，并继续交给 AI 提取。
2. 限制按分块应用，邮件尾部和超出整封链接/图片额度的内容继续进入后续块，不再只取整封前 12000 字符。明显页脚管理链接、跟踪图片等会过滤。
3. 每个块由 AI 结构化提取；即使本地识别了标题边界，也不把本地规则当成最终论文分类器。超长单论文后续片段重复自身上下文，图片链接保存 href/alt，表格标题前的图片与对应论文共同分组。
4. finish_reason=length 立即抛出 output_length；不接受部分 JSON（即使它能解析），也不再对相同大输入进行普通 JSON 修复。失败块先按条目边界二分，必要时按正文进一步拆分。无效 JSON 或响应结构在有意义的情况下也可继续细分。
5. 成功块保留；只有最终仍无法处理的块才使用本地规则补充。跨块重复条目合并，优先保留更丰富的来源片段与图片引用。AI 正常返回空列表时不再用本地规则重新引入导航条目。
6. 默认每封邮件最多 32 次逻辑提取调用、递归深度 4、时间预算 240 秒，并响应取消。32 是 complete_json 调用数，实际 HTTP 次数可能因短暂网络重试/JSON 修复增加；每封时间预算同时限制正在等待的请求。整次运行的 600 秒预算保持。
7. 整封邮件全部成功后才写入生产解析缓存；不缓存带回退的邮件。缓存签名升级，旧版提取结果不会阻止新策略运行。本次不新增持久化的分块缓存。

图片处理保留的是来源引用、替代文字与论文关联，不代表已对图片像素进行 OCR 或视觉分析；不新增网页抓取、全文下载或依赖包。

## 日志与输出

- 截断计入请求状态 output_length，不再显示为 errors=0 的普通成功。
- JSON 解析失败单独记录 validation_failures，包含后续已修复的尝试，与请求层错误分开统计。
- 分块大小、拆分深度、请求序号及原因只写日志，不打断终端进度条。
- 未恢复的失败会列出输出超长、JSON/结构异常、网络超时或预算耗尽等具体类别，不再统一提示等待 API 恢复。
- 发生回退时，继续保留邮件未读、跳过去重索引更新；正常成功路径不变。

配置项位于 `performance.email_max_chunk_items/email_text_max_chars/email_max_links/email_max_images/email_max_split_depth/email_max_requests_per_email/email_budget_seconds`。DeepSeek 的分操作输出额度位于 `llm.operation_settings.email_extraction.max_output_tokens`。

## 验证

真实只读验证使用最新失败的两封邮件：原 HTML 约 28 万和 39 万字符，清理并保留来源关联后分为 PRL 10 块、JACS 13 块。23 次提取请求全部成功，无重试、截断或回退，约 32.8 秒提取 149 个条目（55/94）。结果是模型提取数量，未逐篇人工核验完整性；随后额外通过图片关联与递归边界的离线回归测试。没有重跑整批排序翻译，没有改动 Gmail 状态或论文身份索引。
